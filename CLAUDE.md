# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Grip is a Figma plugin + local Node bridge that exposes full canvas read/write access to MCP agents. Pairs with **Gaffer** (separate tool — see `mcp__gaffer__*`). This file is canonical for architecture; [`TOOLS.md`](./TOOLS.md) is canonical for the tool surface.

## Architecture

One long-lived **daemon** serves three MCP transports against the same `PluginBridge`; its lifetime is independent of any agent:

```
agent ─HTTP MCP──── http://127.0.0.1:7778/mcp ──────────────────────────┐   (direct; no shim)
agent (claude -p) ─stdio MCP─ shim (dist/index.js) ─IPC unix sock─┐      │
agent (claude -p) ─stdio MCP─ shim (dist/index.js) ─IPC unix sock─┤      │
                                                                  ▼      ▼
                              DETACHED daemon (dist/index.js --daemon)
                                • own session, PPID 1 — survives agent kills
                                • HTTP :7778 /mcp  ⇄ direct MCP clients (one McpSession per HTTP session)
                                • IPC unix sock    ⇄ each shim (one McpSession per)
                                • WS :7777 (127.0.0.1 only) ⇄ each Figma plugin iframe ⇄ postMessage ⇄ plugin main
```

Two transports for agents, chosen by how grip is registered in `~/.claude.json`:

- **HTTP (preferred for any MCP client that supports it — Claude Code, desktop agent apps, custom clients):** register `{type:'http', url:'http://127.0.0.1:7778/mcp'}`. The agent connects **directly** to the daemon — no shim, no IPC hop. This removes the leader-death stall class: a call can't be lost in a dying intermediary, and a dead daemon is an instant connection error, not a silent hang. `http-server.ts` runs a stateful `StreamableHTTPServerTransport` per session (one `createSession()` each, reused verbatim). Requires the daemon to be already running → keep it warm with the launchd LaunchAgent (`bridge/scripts/install-launchd.sh`, sets `GRIP_PERSISTENT=1` which disables idle-exit so KeepAlive owns lifecycle).
- **stdio (on-demand, zero-setup):** register `command: dist/index.js` (no flag). That binary is the **shim** by default, **daemon** with `--daemon`. Each agent spawns a shim; the shim probes the IPC socket and, if no daemon, `spawn(detached:true)`s `dist/index.js --daemon` (`stdio:'ignore'`, `.unref()`), waits for the bind, then pipes stdio MCP traffic over IPC. Good for local Claude Code — no always-on daemon needed.
- **Single-instance:** the daemon binds WS `:7777` first (atomic lock); a second daemon losing that bind exits. HTTP `:7778` bind failure is non-fatal (logs + skips HTTP). The launchd install kills any on-demand daemon so the persistent one wins the port.

Implications that span files:

- **stdout is sacred.** Shim stdout is the MCP transport to the agent. All logging goes to **stderr only** (mirrored to `~/.grip-bridge.log`). Any `console.log` corrupts the stream.
- **Per-MCP-session state.** Each transport connection (shim over IPC, or a direct HTTP session) becomes one `McpSession` (`bridge/src/types.ts`) on the daemon, with independent `activeFileId`, `bind`, `subscriptions`, `rateBucket`. `bridge.request(method, params, mcp)` and `bridge.list/setActive(target, mcp)` route by the passed session — no global "active file."
- **File identity: never the `"0:0"` placeholder.** The plugin's hello carries `fileKey = figma.fileKey ?? figma.root.id`, and `root.id` is `"0:0"` in EVERY local/unsaved file, so `fileKey` alone cannot tell such files apart. `fileIdentity(session)` (`ws-server.ts`) is the one identity used by `route()`, `list`, binding, queue re-homing and the `plugin_reconnected` check: a real `fileKey` (`isRealFileKey`: non-empty, not `"0:0"`) when there is one; else, for a key-less file, the hello's `fileUid` (sent by the plugin, see Per-file UID below) TOGETHER WITH the file name; else `undefined`. A `fileUid` never overrides a real key: the plugin re-mints a uid only when it recorded a real key for it, so a uid minted while the key was null is copied into every duplicate, and windows that share a uid but have different real keys are different files. Two key-less windows that share a uid are one file only if their names match; otherwise they are separate entries (an unbound agent gets `ambiguous_active_file`; a `{uid}` bind that matches several entries is `ambiguous_file_name`). Binding to a key-less uid file stores `{uid,name}`, so a later copy under another name never captures it. The stored name is a hint, not a key: it follows the window the agent is pinned to (`refreshBindName`, on every hello of that window and every route), and the bridge follows renames of key-less files (`noteRename`: a window re-saying hello under a new name, or the last window of the old name closing within `RESPAWN_MATCH_MS` (env `GRIP_RESPAWN_MATCH_MS`, 15s) of the first window under the new name, in either order), so `matchBind` and `rehome` still find the file after a rename plus an iframe respawn (`followRename`). A copy that was open long before the original closed, or opened long after, is never taken for it. Sessions with an identity are grouped into one file entry (`distinctOpenFiles`, newest window by first hello wins); identity-less sessions are each their OWN entry (`window:<sessionId>`), never merged. Bindings are never promoted to `"0:0"`: a name target on a key-less file stays `{name}`, a sessionId target becomes `{sessionId,name}` (falls back to the name when that window respawns, then follows the new window), and `set_active_file "0:0"` errors `not_a_file_key`. Only helloed + open sessions count as live (`isLive`); half-connected sockets are counted in `list_files.connecting`, not listed.
- **Agents bind to a file; routing never guesses.** `route()` (`ws-server.ts`) is the single decision, driven by `McpSession.bind` (`FileBind` = `{key?,uid?,name?,sessionId?}`, what the agent WANTS) and `activeFileId` (resolved live pin). Order: (1) live pin still open → route, but if a NEWER live session has the same identity, re-pin to it first (bound agents never keep talking to a dying zombie; an identity-less pin is kept while open, since another window may be another file); (2) `bind` set → `matchBind` (pure: uid, real key, live bound window, then exact name over the file entries); one match → pin + `promote` (name/sessionId → uid or real key when the file has one); a NAME matching >1 entry → **`ambiguous_name`** → `ambiguous_file_name` error listing each candidate (name, fileKey, sessionId), never `bound_file_not_open`; no match → **`deferred`** (never falls to another file); (3) unbound → one entry routes frictionlessly, zero → `plugin_disconnected` after cold-start grace, **>1 entries → `ambiguous_active_file`** naming every file/window (two `"0:0"` windows are two entries, so an unbound agent is never silently routed to whichever said hello last). grip will NOT silently pick among files (the old auto-pick only logged a stderr warning the agent couldn't see → agents landed on the wrong file).
- **Two ways to bind.** Runtime: `set_active_file` accepts fileKey / exact name / sessionId / figma.com URL / fileUid (`resolveBind` + `FIGMA_URL_RE`); binds even if the file isn't open yet (deferred), returning `{bound,resolved,...}` + the open-file list so a typo is caught, plus `warnings[]` when another agent is already bound to the same file. Launch-time: env **`GRIP_FILE=<key|name|url>`** on the agent process; the shim (`proxy.ts`) forwards it as a `{grip:'bind'}` **control frame** (first line on the IPC socket, before MCP traffic); `SocketTransport.onControl` routes it out-of-band (not JSON-RPC) and `ipc-server` calls `bridge.bindFromLaunch`. Agent never calls a tool. Re-sent on every reconnect. Over HTTP there is no shim, so env doesn't reach the daemon per-agent; instead a direct HTTP client adds **`?file=<key|name|url>`** to the `/mcp` URL (read once on the initialize request in `http-server.ts`, like `?tools=`, and applied via the same `bindFromLaunch`). `bindFromLaunch` is lenient: an ambiguous name is kept as a name bind (each call then fails loud with `ambiguous_file_name`) instead of being dropped. Bindings are in memory only: a reaped HTTP session or a daemon restart loses them unless the client reconnects with `?file=` / `GRIP_FILE`.
- **Binding visibility.** `PluginBridge.bindingState(mcp)` reports `{state:'live'|'waiting'|'unbound', target?, sessionId?, fileName?, reason?}` truthfully from `route()`; it feeds `list_files.myBinding`, `grip_health.session.binding` and `get_page_context` (`bind.state` / `binding.state` as `live`/`deferred`/`unbound`; it used to always say `resolved:true`). Cross-agent counts come from `mcp-server.ts` `otherSessions()` (the other `liveSessions`): `list_files` `boundAgents` per file (pure `boundCounts`, never moves another agent's pin), the `set_active_file` collision warning, and `grip_health.otherAgents`. Only counts are exposed, never another agent's id.
- **Sticky across reconnect churn.** Figma respawns plugin iframes every ~1–3min: each is a **new sessionId**. When the live pin dies, `route()` re-resolves from `bind` (re-pins to the same file's newest live session that still matches the bind (`pinMatchesBind` is checked on the re-pin target too, so a pinned agent can never hop); a name/uid bind promotes to `bind.key` on first resolve when the file has a real key, else to `{uid,name}`). When a newer window of a file says hello while older ones are still open, calls still QUEUED (never sent) on the older windows, reads and writes, move to it (`adoptQueued`; `pump()` does the same when it is asked to drain an older window, so nothing queued is ever sent to a replaced window; a moved write keeps its original `GRIP_MAX_WRITE_WAIT_MS` clock); calls already sent stay. If the bound file is fully closed → `deferred` → `bound_file_not_open` after the wait grace (never hops). Sessions carry `helloAt` (last hello: the plugin re-sends hello on every page switch) and `firstHelloAt` + `helloSeq` (first hello, never bumped). Every "which window of a file is newer" decision (`newestLive` routing newest-wins, `distinctOpenFiles`, `adoptQueued`, the per-file write lane, `onTimeout`'s reconnect check) uses the FIRST hello (`isNewer`), so routing never lands on a dying zombie and a page switch in an older window never makes it look newer than the iframe that replaced it. This all exists because a dead pin + two open files used to make page-scoped reads (`figma.currentPage.findAll`, `.selection`) silently hit the *wrong file's* page and return `[]`: a false-negative, not an error. Known gap: two `"0:0"` windows of the SAME file with no `fileUid` (older plugin, view-only file) or caught mid-rename (names differ) can't be told apart from two different files, so an unbound agent may briefly see `ambiguous_active_file` during that overlap (the error says to retry); a bound agent keeps its pinned window.
- **Plugin sessions.** Many Figma windows can run the plugin at once. Each opens its own WebSocket to the daemon; plugin replies with a `hello` carrying `version`/`capabilities`/`fileKey`/`fileName`/page. Fan-out by design.
- **Correlation by UUID.** `bridge/src/ws-server.ts` keeps `Map<uuid, {...}>` for in-flight WS requests. 10s timeout + 5s heartbeat (`ws.ping`); dead plugin → reads and never-sent calls are re-sent once on the file's next session, sent changes fail with `maybe_applied` (see Error handling contract). Response >8MB rejected with `response_too_large`.
- **Plugin main thread is the only place Figma API runs.** `plugin/code.ts` dispatches by `method`, serializes, returns via `postMessage`. UI iframe (`plugin/ui.html`) is a thin relay + 32px status strip — it owns the WebSocket and **forwards the full `hello` (incl. version/capabilities)**; an earlier allow-list that dropped fields caused a long false-positive cache hunt.
  - **Mutating calls are serialized inside the plugin (per file).** The async handler interleaves at every `await`; with each write bracketed by `commitUndo()` at start and end, two agents' half-done writes used to split or merge Cmd-Z steps. `figma.ui.onmessage` now runs every method NOT in `READ_ONLY_METHODS` (run_script included) through `createMutationQueue` (a promise-chain FIFO, between the `grip:mutation-queue` markers in code.ts): one write at a time, in arrival order, so one tool call = exactly one undo step. Reads never wait and still run concurrently. `commit_undo`/`trigger_undo` are not undo-bracketed but do take the queue, so they act on a finished step (trigger_undo still undoes the file's last step, which may be another agent's or the user's). Liveness: try/finally releases on throw; a write whose budget is used up while it waits (`mutationQueueOpts`/`requestBudgetMs`, between the `grip:request-budget` markers: the request frame's `timeoutMs`, which the bridge always sends and `ui.html` forwards with every other frame field, else the 10s / run_script `timeoutMs` / map_nodes 60s table; less a 250ms transport margin) is NOT started and fails with `plugin_queue_timeout` (the bridge has given up on it, so starting it late would change the document behind the agent). Exact guarantee: a write that STARTED inside its budget cannot be aborted; if the bridge times it out meanwhile it may still be applied, and the bridge's `request_timeout` for a change says `maybe_applied`. The bridge's write lane (below) means writes normally never wait here; a write that never settles is released after budget + 5s (max 125s) with a console warning. `busy:true` is posted on arrival and exactly one `busy:false` when done, so queued calls keep the strip pulsing.
  - **Per-invocation yield clock.** `createYieldClock()` (marker block `grip:yield-clock`) makes one pacing clock per run_script and per forEachNode/mapNodes run; there is no shared module-level clock, so concurrent work never resets another run's pacing. Script-visible helper signatures are unchanged.
  - **Per-file UID in `hello`.** `fileUid()` reads `figma.root.getPluginData('grip.fileUid')`, minting a random UUID with `setPluginData` on first use (also stores the fileKey it was minted for in `grip.fileUidFileKey`; a mismatch with a real current fileKey means "duplicate of another cloud file" and re-mints). Failure (view-only, Dev Mode) means no `fileUid` in hello. Catch: duplicating a file copies plugin data, and a uid minted while `figma.fileKey` was null is never re-minted, so two files can share a UID; the bridge therefore prefers a real key over the uid and, for key-less files, counts the uid only together with the name (see File identity). Capability flag `fileUid`.
  - **Page side effects are opt-out.** `set_selection`/`scroll_to` still switch to the nodes' page by default; `keepPage:true` never switches and fails with `node_on_other_page`. `get_selection`, `find_with_criteria` and `create_node` (no parentId) take `pageId` and work on that page object (`loadedPage()`: getNode + loadAsync) without touching `figma.currentPage`. Capability flag `keepPage`.
  - **documentchange origins.** The event payload is `{changes, origins:{LOCAL, REMOTE}}`, accumulated over the whole 500ms debounce window (before, only the last batch survived). LOCAL includes this plugin's own writes. Capability flag `docChangeOrigins`.
- **Reads are bounded by default.** `get_node`/`get_nodes`/`get_selection` default to depth 12 + a 3000-node budget (`maxNodes`); children beyond collapse to stubs with `truncated:true`. Pass `depth:-1` + `maxNodes:0` for full fidelity. Unbounded reads were the `get_selection` 128s-stall cause.
- **Read payload cap (`read_too_large`).** The node budget bounds node *count*, not payload *bytes* — a small-but-deep full serialize (e.g. 59 nodes × ~3.7k chars = 219KB) sailed under the 8MB WS cap but overflowed the MCP client's token budget AND re-cost context every turn. `ws-server.ts` rejects a read result over `READ_SOFT_CAP_BYTES` (env `GRIP_READ_CAP_BYTES`, default 120KB) for read methods with an actionable `read_too_large` naming the remedy (pass `properties`, lower `depth`, or `export_node` JSON to disk). Distinct from the 8MB `response_too_large` OOM backstop. A `properties` whitelist recurses to every node in the tree (not just the root) — pass e.g. `properties:['name','variantProperties']` for a lean recursive read; it also skips the per-INSTANCE `getMainComponentAsync` unless `componentId`/`componentName` is requested.
- **Perf gotcha — first touch of a REMOTE (library) component set is slow.** The first `set_node_property componentProperties` / `swap_instance` / variant `setProperties` against a remote component set makes Figma load that set (~1–2s); subsequent touches are ms. This cost is Figma-inherent (loading the remote set) — grip can't shrink a single first-touch. It only bit as a *batch* failure (5 sequential swaps overran the 10s budget on the cold load); that's now covered by run_script's opt-in `timeoutMs` (max 120s). If you still want each call fast: split the first swap into its own call (warms it), or touch one instance of the set first, then batch the rest.
- **A `set_active_file` (or `GRIP_FILE`) binding survives plugin reconnects; auto-route does not.** `mcp.bind` is only ever set by `set_active_file`/`bindFromLaunch` and is never cleared on reconnect: `route()` clears just the resolved `activeFileId` and re-resolves it from the durable `bind` (newest live session for that file identity). An UNBOUND agent (relying on single-open-file auto-routing) has nothing to survive, so during reconnect churn it can briefly see `ambiguous_active_file` or, for a call that could not be re-sent, `plugin_reconnected` (reads and never-sent calls are re-sent once automatically, see the flow-control bullets; a change that was already sent fails with `maybe_applied`): bind to avoid that window. (A `bind: null` in `get_page_context` means the agent never bound, not that a binding was lost.)
- **Pairing (`pairing.ts`, gate in `ws-server.ts`, handshake in `figma-plugin/ui.html`).** The WS has no sign-in and Figma's plugin iframe sends Origin `"null"`, which any sandboxed iframe or `data:` page also sends, so origin alone cannot tell the plugin from a web page; a local process squatting `::1:7777`/`127.0.0.1:7777` (the plugin dials `localhost`, which macOS resolves to `::1` first) could also pose as the bridge. A shared secret fixes both. Tokens `{id, secret}` live in `<GRIP_HOME>/pairing.json` (0600, re-read when mtime changes, so the CLI needs no IPC) and in the plugin's `clientStorage` key `grip.pairing` (written by `code.ts`; the `client_storage` tool refuses `grip.` keys, `inspectScript` nudges). Per connection the welcome carries a nonce; a paired plugin sends `{type:'auth', tokenId, nonce, proof}` (`proof = HMAC-SHA256(secret, "<label>|plugin|<bridgeNonce>|<pluginNonce>")`, label `grip-auth` for slug `grip`, `grip-auth:<slug>` for any other flavour), the bridge verifies and answers `auth_ok` with the `bridge` proof, and the plugin verifies THAT before it sends a hello (so a squatter never learns a file name or key) or obeys a request. The secret never crosses the wire; the plugin's SHA-256/HMAC is plain JS in `ui.html` (checked against node:crypto in `test/pairing.mjs`). The welcome, hello, auth and pair_request frames carry a `flavour` field (absent = `grip`, so old plugins keep working); the bridge checks it unconditionally BEFORE the pairing gate (`refuseFlavour`, `ws-server.ts`) and closes a mismatch with code 4409 `flavour mismatch`, never looking at that socket again; the plugin refuses a bridge of another flavour the same way (yellow strip "Wrong Grip build", retry about every 8 s). Unpaired plugins send `{type:'pair_request'}`: granted only while a window opened on this machine is open (CLI `pair`, 120s; the installer's 5 minutes; one grant closes it) or, in `auto` mode, while nothing is paired yet (trust on first use); else `pair_denied`. Once a token exists, or in `required` mode, the bridge enforces: `Session.authed` is false until a proof or grant, `handleMessage` looks at nothing but `auth`/`pair_request` before that (no hello, response, event or update_request from an unpaired socket), and sockets that were let in before enforcement began are closed (`dropUnpaired`); a legacy plugin that says hello gets one throttled toast (5 min) and is closed 4403. **Modes:** the mode is `GRIP_PAIRING` if set, else `required` when `pairing.json` has `"required":true`, else `auto`. A FRESH install (`install.ts` `preparePairing` -> `prepareInstall`, only when no `pairing.json` exists) writes `{required:true,tokens:[]}` and opens a 5 minute window, so a fresh install has NO open-ended trust on first use: a web page that connects first, or with no window open, gets `pair_denied` and is never routed (`test/pairing.mjs` section 3). Installs that predate this (no `pairing.json`) stay in `auto` so an update never strands a working setup (a self-update opens no window and sets no flag); `pair --require` switches them, `pair --auto` goes back; both flags survive grants and `pair --reset`. A bridge without pairing sends no nonce; the plugin accepts that only if it never paired (a stored token + no nonce = downgrade, refused). `GRIP_PAIRING`: `auto` (default), `off` (old open behaviour, no nonce), `required` (enforced even with no token). `PluginBridge`'s second constructor argument `{pairing}` is what turns it on: only the daemon passes it, so every in-process test keeps the open behaviour. Known limits: pairing cannot tell the real plugin from other local software at the very first pairing of an install (the installer's short window, or on installs that predate required mode the first plugin that connects), so the recovery is visible instead: a plugin refused right after another client paired says so (`recentGrant`), `pair --reset` then `pair` starts over, and `grip_health.pairing` shows when and from where the last pairing happened. A window re-reads its stored token on every connect (another window may have paired since). `grip_health.plugins[].paired` / `.reserved` show a socket that proved itself / queued in the reserved pool; the ticket URL is accepted by real Figma.
- **Peer limits and bad frames.** `handleMessage` accepts only JSON objects and the message listener has a try/catch (one `null` frame used to crash the daemon; `index.ts` also installs `uncaughtException`/`unhandledRejection` handlers in the daemon that log the message and carry on, exiting only after 20 faults in a minute). `update_request` and `event` frames from a socket that has not said hello are ignored (an event silently, since a real window forwards `selectionchange` while its hello is on the way; an `update_request` with one neutral, rate-limited line). Hello fields are typed and bounded by `clip()` (control characters stripped, names 256, keys 128): they reach logs and tool results. WS: `GRIP_MAX_SOCKETS` (64), `GRIP_MAX_UNHELLOED` (16), `GRIP_HELLO_DEADLINE_MS` (5s, close 4408); when a limit is reached the OLDEST socket that never said hello is evicted (1013) so a page cannot lock the real plugin out by connecting first; a paired plugin puts the id of its stored token in the connect URL (`ws://localhost:7777/?t=<id>`, never the secret; `ui.html` waits up to 1.5s for the stored token before its first connect) and queues in a RESERVED pool (`GRIP_MAX_RESERVED`, 8) that anonymous churn cannot touch, because a page cannot learn the id; the claim only picks the pool, trust still comes from the proof. If Figma refused a URL with a query (unverified in a real Figma), every third attempt goes without it and a ticketless success drops it for that window. A socket that has proven itself (`tokenId`) is never evicted. Connection slots that anything on this machine can open before it proves itself cannot be fully protected, so that pool is availability-only and never a way to take over a paired plugin. Lines about refused/evicted peers clip the attacker-controlled Origin/Host and are rate-limited to one per second (`logRefused`). IPC framing (`socket-transport.ts`) parks newline-less chunks without rescanning them (linear in the data received) and closes a connection past 10MB; a connection may park at most `GRIP_IPC_FIRST_FRAME_BYTES` (1MB) until it has delivered one valid frame, all connections together at most `GRIP_IPC_PARKED_BYTES` (64MB) of unfinished frames (the offender is closed), and the IPC server takes at most `GRIP_MAX_IPC` (128) connections. HTTP: `GRIP_MAX_HTTP_SESSIONS` (64) / `GRIP_MAX_HTTP_PENDING` (16), 503 beyond. The log mirror is 0600 and rotates to `<log>.1` at `GRIP_LOG_MAX_BYTES` (10MB); status and dump files are 0600.
- **File and URL guards (`guards.ts`).** The bridge touches the user's disk on an agent's say-so in two tools, and an agent can be steered by text in a Figma file. `upload_image_from_path`: inside home/temp (+`GRIP_ALLOWED_DIRS`), no hidden component, no `~/Library`, symlinks resolved first, regular file <= 64MB with image magic bytes. `export_node` with `path`: same location rules, the format's own extension, existing file only with `overwrite:true`, never through a symlink. `open_external_url`/`create_image_from_url`/`create_link_preview`: public http(s) only (`checkWebUrl`: the URL is parsed, the host judged as an IPv4/IPv6 address (IPv4-mapped, NAT64, 6to4, CGNAT 100.64/10, trailing dots) or a name (single-label and `.local`/`.internal`/`.lan`... refused; a DNS name that RESOLVES locally cannot be caught); the plugin's `assertWebUrl` only checks the scheme). `GRIP_ALLOW_ANY_PATH=1` switches the location rules off (image-only and extension rules stay), `GRIP_ALLOW_LOCAL_URLS=1` allows local URLs. The session `instructions` also tell the agent that document text is untrusted data. These are guardrails against a steered agent, not a boundary: `run_script` can do anything the plugin can.
- **Network exposure (loopback only, web pages refused).** The plugin WebSocket has no authentication, so reachability IS the security model. `WS_HOST` (`ws-server.ts`) is `127.0.0.1`: `new WebSocketServer({port})` without `host` binds every interface (`*:7777`) and was the 0.9.5 fix, so never drop `host`. Loopback alone is not enough: a web page can open `ws://127.0.0.1:7777`, so `verifyClient` refuses any handshake whose Origin is not absent, `"null"` (Figma's sandboxed plugin iframe) or figma.com (`originAllowedForUpdate`, same rule as the `update_request` check, kept as defense in depth). HTTP `:7778` is also loopback, and `onRequest` (`http-server.ts`) refuses a Host that is not a loopback name (DNS rebinding) and any Origin that is not an http(s) loopback origin (native MCP clients send none), because that endpoint reaches `run_script`. `test/network-exposure.mjs` checks every non-loopback address of the machine refuses the WS and the Origin/Host rules. There is deliberately no token: the Community plugin cannot read `~/.grip`, so a secret would have nowhere to live; a same-user local process is out of scope.
- **Never read `err.stack` on hot paths.** Accessing it triggers V8's `CallPrinter`/`Scanner` source walk and pegs CPU at 100% (an "eager drain" we added then reverted). `Error.stackTraceLimit = 3` is set in `index.ts`; handlers log `err.message` only.
- **Self-update (user-triggered, never automatic) from GitHub Releases, compatibility-gated.** Releases are built and signed by CI (`.github/workflows/release.yml`) and carry 9 assets (public flavour; a `payloadLoader` flavour adds a 10th, `grip-plugin-payload.json`): `grip-bridge.mjs`, `grip-plugin-code.js`, `grip-plugin-ui.html`, `grip-plugin-manifest.json` (plain copies of `figma-plugin/*`, so the in-place updater downloads files, not a zip), `grip-install.zip` (`grip/bridge/{grip-bridge.mjs,install.mjs}` + `grip/figma-plugin/*` + `grip/THIRD-PARTY-NOTICES.txt`, what the README install steps and manual users use; the installer ships ONLY in the zip, never as a loose asset, because alone it cannot run — it reads `grip-bridge.mjs` next to itself), `THIRD-PARTY-NOTICES.txt` (licenses of the bundled dependencies; the updater never downloads it), `compat.json`, `SHA256SUMS.txt` and `SHA256SUMS.txt.sig` (the Ed25519 signature over `SHA256SUMS.txt`, see **Signed releases**). There is no `version.json`. The release body is the CHANGELOG section plus an install footer after a `<!-- grip-install -->` marker line (`release-gate.mjs` `withInstallFooter`: "tell your agent `Install Grip from https://github.com/spendolas/grip/releases/latest`" + a tag-pinned README link); `update.ts` `releaseNotes()`/`releaseHeadline()` cut from that marker, so notices never carry it.
  - **Compatibility (the most important rule).** The published plugin is updated through Figma, NOT by this updater, so a user's plugin can lag or lead the bridge. `MIN_PLUGIN_VERSION` (`types.ts`, currently `0.6.0`: the first plugin with the `hello` contract (version/capabilities/fileKey); older plugins can lack newer methods, which the bridge turns into a per-tool "older build" error, so the minimum is deliberately low) is the oldest plugin this bridge supports. `scripts/package-release.mjs` writes `compat.json` = `{version: BRIDGE_VERSION, minPlugin: MIN_PLUGIN_VERSION, flavour: <flavour.json slug>, protocol: PROTOCOL_VERSION, minPluginProtocol: MIN_PLUGIN_PROTOCOL}` FROM `types.ts` + the flavour file (no hand-edited copy; it refuses a release whose plugin `PROTOCOL_VERSION` is below `MIN_PLUGIN_PROTOCOL` or whose bridge `PROTOCOL_VERSION` is below the plugin's `MIN_BRIDGE_PROTOCOL`) and lists it in `SHA256SUMS.txt`; `release-gate.mjs` requires it; a test keeps update.ts, packager and gate asset names in step. The check fetches `compat.json` + `SHA256SUMS.txt` (small), verifies compat.json against the sums, stores `minPlugin` + `minPluginProtocol` in state + `~/.grip/update-check.json`. No/unverifiable compat.json = `minPlugin:null` + `compatError`: reported as `available` but NOT signalled and NOT installable (fail closed; only CLI `--force`, with a loud warning). **`updateSignal(state, plugins)`** is the single decision for every surface (purple strip push, session `instructions` paragraph, first-tool-result notice, `grip_health.update`): signal only when update available AND >=1 connected (helloed, ws-ready) plugin has a KNOWN version >= `minPlugin` (unknown = incompatible). **Protocol integers:** `PROTOCOL_VERSION` / `MIN_PLUGIN_PROTOCOL` (`types.ts`) and `PROTOCOL_VERSION` / `MIN_BRIDGE_PROTOCOL` (`plugin/code.ts`); the welcome carries the bridge's `protocol`, the hello carries `protocol` + `minBridgeProtocol`. When both sides report one, the integer alone decides, symmetrically: a plugin is judged by `minPluginProtocol` instead of `minPlugin` (`pluginIncompatibility`), a bridge by `minBridgeProtocol` instead of `minBridge` (`bridgeStaleFor`, the one rule behind `bridgeStaleReason` and the hello warning; `ui.html` `bridgeOutdated()` mirrors it); when either number is absent, the version rule. Signalling is **per window**: the strip push uses `UpdateBroadcast.eligible(sessionId)`, so only a compatible window turns purple and an old window neither gets the signal nor blocks the others; old windows are reported as `staleWindows` (health, agent `check` note, CLI warning, install result: after the update that window's plugin must be updated in Figma). `blockedReason` (only when NO window is compatible) e.g. `plugin 0.6.0 in "Fidelity" is older than 0.9.0 requires (>=0.8.0); update the Grip plugin in Figma first`. `wireUpdateToBridge` recomputes on update-state changes AND on every plugin connect/disconnect (`session-change`). Install re-verifies the same rule against the sessions connected NOW on every route (`incompatible_plugin`; tool with no plugin: `plugins_unverifiable` = "open the Grip plugin in Figma first"; WS: the requesting window's plugin must itself be compatible, else `incompatible_plugin`; CLI: reads the plugin list from the daemon status file `~/.grip-bridge.status` `plugins[]`, `readDaemonPlugins()`, and when it cannot tell prints that and needs `--yes`/`--force`; a KNOWN-incompatible plugin refuses even `--force`). The reverse direction: the plugin's `hello` carries `minBridge` (`MIN_BRIDGE_VERSION` in `plugin/code.ts`, currently `0.8.0` = the first bridge that can update itself). Bridge side: a plugin that needs a newer bridge (`bridgeStaleFor`: `minBridgeProtocol > PROTOCOL_VERSION` when it names one, else `minBridge > BRIDGE_VERSION`) is logged and shown in `grip_health.update` (`bridgeStale`, `updateRecommended`). Plugin side (`ui.html` `bridgeOutdated()`): when the bridge is older than the plugin wants (welcome `protocol` < `minBridgeProtocol` when both exist, else welcome `bridgeVersion` < `minBridge`) and the bridge has not offered an in-place update, the strip turns purple (+`actionable`), tooltip "Bridge update needed. Click for steps", and the click depends on the bridge: a bridge from 0.8.0 on hears update requests, so the click sends `update_request {version:'latest'}` (tooltip "Bridge update needed. Click to update"; the bridge accepts `latest` only from a window whose plugin needs a newer bridge, looks the release up fresh and then applies the same pin, compat and verification steps as any install; answers `no_update_available` when nothing newer is published); only an older bridge, which cannot hear it, gets the install page (a plugin cannot install a bridge: no filesystem or process access). An offered in-place update always wins. **Releasing rule:** raising `MIN_PLUGIN_VERSION` means publishing the new plugin in Figma BEFORE cutting the bridge release + a CHANGELOG line saying the plugin must be updated first (README -> Releasing). Plugins that report `protocol` are judged by `MIN_PLUGIN_PROTOCOL` instead, so a bump that must reach them raises the protocol integer too (`MIN_BRIDGE_PROTOCOL` likewise for the reverse direction).
  - **Signed releases (checked before anything else; `--force` cannot bypass it).** `SHA256SUMS.txt` comes from the same release as the files it lists, so by itself it only catches corruption: whoever controls the repo/release would control what every install runs. So every release carries `SHA256SUMS.txt.sig`, an Ed25519 signature (node:crypto, no dependency) over the exact bytes of `SHA256SUMS.txt`: the raw 64-byte signature, base64, one line, made in CI by `scripts/sign-release.mjs` with a private key that lives only in the repository secret `GRIP_RELEASE_SIGNING_KEY` (PKCS8 PEM). The public key(s) are pinned in `flavour/flavour.json` `releaseKeys` (`update.ts` `RELEASE_PUBLIC_KEYS = FLAVOUR.releaseKeys`; an ARRAY of SPKI PEM strings, so a key is rotated by shipping a bridge that trusts old and new, then signing with the new one; the PEM header is the one `bundle-hygiene.mjs` ALLOWLIST entry, a public key being no secret). `fetchSums` (the only place the sums are read, for the check AND for `installUpdate`) downloads the sums, then `SHA256SUMS.txt.sig` (same host allowlist, 1KB cap), and `crypto.verify(null, sums, key, sig)` against any trusted key BEFORE a single line is parsed; compat.json, every file hash and the plugin/bridge downloads all hang off those verified sums. Missing signature asset => `UpdateError` `signature_missing`; present but wrong (tampered sums, another key, garbage, wrong length) => `signature_invalid`. Both fail closed exactly like a missing compat.json: the check still reports `available:true` but the state carries `signatureError` (and `minPlugin:null`), so `updateSignal` withholds the signal (`blockedReason` "Grip X is not offered: ..."), the strip never turns purple, `grip_update {check}` and `grip_health.update` carry `signatureError`, and `installUpdate` throws the typed error (tool: `signature_invalid: update failed: ...`; WS: `update_result` `code`; CLI: "Not installing", exit 1) after recording the state, before the version pin, the confirm prompt or any payload download. Unlike `compat_unverified`, NO flag overrides it: the CLI prints "--force does not override a signature failure". A failure to DOWNLOAD the sig (network, size, host) is an ordinary `compatError`, not a signature verdict. `~/.grip/update-check.json` carries `signed:true` next to `minPlugin`; a cache without it (written by a pre-signing bridge) is not believed, so a stale unsigned `minPlugin` never signals. **Test-only override:** env `GRIP_RELEASE_PUBKEY` (PEM text) REPLACES the pinned list, but only when `GRIP_TEST=1` is also set (otherwise it is ignored with one stderr notice, so an environment variable on the daemon cannot point it at another key; `GRIP_RELEASES_API` is a separate override and is NOT gated by `GRIP_TEST`; on a `lockOverrides:true` flavour BOTH `GRIP_RELEASES_API` and `GRIP_RELEASE_PUBKEY` are ignored, even with `GRIP_TEST=1`); it can only substitute a key: empty means the pinned keys, and an unusable value leaves NO trusted key (everything fails closed), never "skip verification". The tests (`src/bridge/test/update.mjs`, `scripts/sign-release.test.mjs`) sign with a THROWAWAY keypair committed as inline PEM; the real private key is never in the repo. **Flavour claim (`flavour_mismatch`).** compat.json is listed in the signed sums, so its `flavour` is a signed claim: `fetchCompat` checks it before anything else in the file, and a release for another flavour (an ABSENT claim means `grip`, which every release before the field was) throws `flavour_mismatch`; `--force` never overrides it. `isTrustFailure(code)` (`signature_*` or `flavour_mismatch`) is the single predicate for both: `signatureError` also carries flavour mismatches, `UpdateState.trustCode` names the code (shown as `grip_health.update.trustCode`).
  - **Flow (`update.ts`).** The daemon asks `GET https://api.github.com/repos/spendolas/grip/releases/latest` (the flavour's `releasesApi`; env `GRIP_RELEASES_API` = full URL override for tests/forks, ignored on a locked flavour; https, or http on 127.0.0.1/localhost; `Accept: application/vnd.github+json`, `User-Agent: grip-bridge/<version>` and nothing else: no identifier) ~30s after start and every 24h (`GRIP_NO_UPDATE_CHECK=1` disables the automatic checks, the purple strip and every notice), parses `tag_name` (strip `v`), `body` and the asset list (drafts/prereleases ignored; **asset-URL pin** (`update-policy.ts` `downloadPrefixFor`): only when the releases URL has the standard `https://api.github.com/repos/<o>/<r>/releases/latest` shape, an asset whose normalised `browser_download_url` is not under `https://github.com/<o>/<r>/releases/download/` (compared case-insensitively) is dropped and its NAME (never the URL) logged once per parse; any other shape, e.g. a test server, is not pinned, so `gen-flavour.mjs` requires that shape when `lockOverrides:true`), caches `{latest, headline, notes, minPlugin, minPluginProtocol, notifiedAt}` in memory + `~/.grip/update-check.json`. Surfaces: (a) agents: session `instructions` paragraph + one extra text block on the first successful tool result of a session (both carry the release **headline**) + `grip_health.update` `{current, latest, available, checkedAt, minPlugin, minPluginProtocol, signalled, signatureError?, trustCode?, blockedReason?, bridgeStale?}` (always the truth); the agent NOTICE (not health/check) for a given `latest` is shown **at most once per 3 days across sessions** (`claimNotice`, `notifiedAt[version]` in update-check.json, honours `GRIP_HOME`); `grip_update {action:'check'}` returns headline/notes + `signalled`/`blockedReason`; (b) the plugin strip: WS `{type:'update', available:<signal>, latest, current, headline}` on hello/change (deduped per session), `ui.html` turns **purple** (`#A855F7`, pulsing) when connected + signalled; hover tooltip "Grip update available (0.8.0 → 0.9.0) — click to install" + headline; ONE click sends `{type:'update_request', version:'<shown>'}` (no two-click confirm, no label); the bridge installs only if the latest release still equals that version, else `update_result {status:'error', code:'version_changed', latest}` and re-pushes the state; answered with `{type:'update_result', status:'updated'|'up_to_date'|'already_installing'|'clone_install'|'error', from?, to?, restart?, next?, code?, message?, latest?}` (error codes: version_changed, incompatible_plugin, plugins_unverifiable, compat_unverified, signature_missing, signature_invalid, flavour_mismatch, selftest_failed, version_required, origin, install_failed); the bridge refuses `update_request` from a browser-page Origin (only absent/`null`/figma.com); (c) the agent tool `grip_update {action:'check'|'install', version}` and (d) CLI `node ~/.grip/grip-bridge.mjs update [--check|--yes|--rollback|--force]` (parsed first in `index.ts`, starts no daemon; prints the notes).
  - **Install (`installUpdate`, shared by all routes).** Order: fetch release -> up_to_date? -> clone guard -> sums signature verified, then sums + compat.json verified (state refreshed) -> **version pin** (`version` must equal the latest, else `version_changed` with the new notes) -> plugin compat vs sessions connected now -> optional `confirm()` callback (tool elicitation) -> download `grip-bridge.mjs` and the three `grip-plugin-*` assets via each asset's `browser_download_url`; **hosts allowlist** (`github.com`, `api.github.com`, `*.githubusercontent.com`, https only, no odd ports; plus the `GRIP_RELEASES_API` origin for tests) checked on the first URL and every redirect hop (max 3), size caps (5MB per file), **every file must be listed in the (signature-verified) `SHA256SUMS.txt` AND match**, ALL verified in memory before the first write -> **self-test**: the new bridge is written next to the target and run once with `--selftest` (`index.ts` early exit: prints `grip-bridge <version> ok`, binds no ports, touches no `~/.grip`) via `process.execPath`, 10s timeout (`GRIP_SELFTEST_TIMEOUT_MS` can only lower it); a non-zero exit, wrong output or timeout aborts with nothing changed -> atomic tmp+rename into `GRIP_HOME` (default `~/.grip`; `figma-plugin/{code.js,ui.html,manifest.json}`; previous bridge kept as `grip-bridge.prev.mjs`), bridge last, then `install.json`. Rollback (`update --rollback`) restores the bridge only; plugin files stay at the new version. The daemon then restarts itself ~1s later (`restartDaemon` in `index.ts`): `GRIP_SUPERVISED=1` (macOS Login Item loop / systemd unit) -> `exit(0)` and the supervisor starts the new file; otherwise it releases its ports and spawns a detached replacement (`GRIP_RESTART_WAIT=1` makes it wait for `:7777`). stdio shims need no change. The plugin strip polls every 250ms while "Updating…" so the reconnect is quick.
  - **Agent tool consent (enforced, not just requested).** `grip_update {action:'install', version:'<x.y.z>'}`: `version` is REQUIRED (`version_required`) and must equal the current latest (`version_changed` error with the new version/notes). If the MCP client advertises `elicitation` (`server.getClientCapabilities()?.elicitation`; `{form}` or the legacy empty `{}`), the bridge calls `server.elicitInput` with a form-less "Install Grip x -> y? <headline>" and proceeds only on `accept` (decline/cancel/error/60s timeout -> `{status:'declined'}`; `GRIP_ELICIT_TIMEOUT_MS` can only lower it); the result carries `consent:'user_confirmed'`. Clients without elicitation proceed on the version pin alone (`consent:'agent_attested'`; the tool text says the agent must have the user's explicit yes). Guidance lives in the tool's `detail` (`grip_capabilities {tool:'grip_update'}`), not its description, so the `scope.mjs` core-description byte budget (7100) is unchanged.
  - **Install source tracking:** the installer writes `~/.grip/install.json` `{source:'release'|'clone', version}` — `clone` when `install.mjs` sits inside a git work tree (a `.git` dir or file found walking up: `detectInstallSource`), `release` when it runs from an extracted `grip-install.zip`. For a `clone` install `installUpdate()` never overwrites: it returns `{status:'clone_install', from, to, next:['git pull','node bridge/install.mjs']}` (tool, WS and CLI all surface it; `check` still reports availability; the strip stops being purple); only the CLI's `--force` overrides (and flips the record to `release`). A missing `install.json` (pre-0.8 installs) counts as `release`. Installer re-runs also stop a verified old daemon (`stopRunningDaemon`: pid from the status file, command line must contain `grip-bridge` + `--daemon`). Plugin WS frames are additive: old plugins/bridges ignore the new `type` messages and fields.
- **Imported plugin copies + agent help for the rest (`update.ts`).** The release updater writes `~/.grip/figma-plugin`; a plugin imported into Figma from ANOTHER folder would never change. Figma lists every imported dev plugin in its `settings.json` (`localFileExtensions`: macOS `~/Library/Application Support/Figma/`, Windows `%APPDATA%\Figma\`; env `GRIP_FIGMA_SETTINGS` overrides), so `findPluginCopies()` (5s memo) finds each folder whose `manifest.json` id equals the installed manifest's id (only that list is read), classifies it (`git_checkout` = inside a git work tree, never written; `not_a_plain_copy`; `unreadable`) and compares its `PLUGIN_VERSION` with `installedPluginVersion()` (the `~/.grip/figma-plugin/code.js`, mtime-cached). `syncPluginCopies()` copies the three installed files into every behind, plain, non-git copy (atomic, manifest last, never a downgrade, never throws); it runs at the end of `installUpdate` (result `pluginCopies:{updated,skipped}`) and from the strip: with no bridge update on offer but a copy behind, `wireUpdateToBridge` pushes the purple strip (`latest` = installed plugin version, `current` = oldest copy, headline "Refresh the Grip plugin you imported (n folders)", `eligible` = windows older than the installed plugin); the click (`update_request` whose version is the installed plugin's and matches no bridge update, `copyRefreshRequested`) answers `{status:'updated', restart:'none', copies:n}`. A dev plugin hot-swaps when its files change, so nothing else is asked of anyone. After a successful install `installUpdate` writes `~/.grip/update-done.json` `{version, from, at, refreshed}`; the restarted bridge (`readUpdateMarker`: only for its own `BRIDGE_VERSION`, max 10 min old, a stale one is deleted) shows each open file ONE toast "Grip updated to x.", keyed by fileKey|fileName so reconnect churn does not repeat it, merged with the reopen nudge when both apply ("Grip updated to x. Reopen the plugin to load its new version."; kept short on purpose); a failed `update_request` also toasts "Grip could not update: <reason>" in the clicking window (not for `version_changed`). All via `PluginBridge.toast`. A COMMUNITY plugin (Figma's list readable, no imported Grip copy) older than the installed plugin cannot be reached from disk and a plugin cannot reload itself (the Plugin API has no reload/relaunch; `closePlugin` only closes): `wireUpdateToBridge`'s `nudgeReopen` sends ONE toast to that window via `PluginBridge.toast(sessionId, msg)` (fire-and-forget frame calling the plugin's own `notify` method, so any plugin version works; `claimNotice('reopen:<file>|<running>|<installed>')` once per 3 days, in-memory set per run, none when a dev copy exists or checks are off) and `helpNotices` carries a hedged agent line (Figma may not have published the new version yet). The reopen nudge and the agent's reopen line apply whenever NO imported copy still needs work (`copyNeedsWork`: behind, or unreadable version; a CURRENT copy, even a git checkout, never blocks it) and not within 60s after a refresh (`recentlySynced`: the dev window is about to hot-swap); an imported copy that is behind goes to the strip (refreshable) or to the agent's git-pull text (git checkout / not a plain copy). The agent (`helpNotices`: `plugin-behind:<v>` / `bridge-behind:<v>`, session `instructions` + one extra block on the first successful result, `claimNotice` throttle once per 3 days, silenced by `GRIP_NO_UPDATE_CHECK=1`) hears only about what the bridge cannot do: a window behind with only skipped copies, or Figma's list unreadable (origin unknown); NOT for a refreshable copy (the strip), nor when Figma's list is readable and has no Grip copy (a Community plugin, Figma updates it). Bridge side: a plugin needing a newer bridge notifies the agent only when no update is offered or the bridge is a clone. `grip_health.update` always carries `pluginBehind`, `pluginCopies:{refreshable,needsYou}`, `pluginHelp`, `bridgeHelp`. Test: `test/help-notice.mjs` (+ `update.mjs` 2b).
- **Loader shell (flavours with `payloadLoader: true` only; the public flavour never takes these paths).** The plugin published to the Figma org is a tiny shell that runs a SIGNED payload the bridge hands it: `src/plugin/shell/` (shell main thread `shell-code.js`, loader + verifier injected into the unedited `templates/ui.html` by `assemble.mjs`), `scripts/build-shell.mjs` (turns the full compiled plugin into `build/payload/code.js`, rewriting `figma.showUI/ui.onmessage/on/once/off` to the `__shell` host), `scripts/payload.mjs` (envelope, `signingMessage`, CI signer; release key = `releaseKeys`), bridge `payload.ts` (serves `<home>/figma-plugin/payload.json` after the pairing gate on `payload_have`) and the updater (`ASSET_PAYLOAD`, `pluginAssets()`). The shell verifies Ed25519 in pure JS in the iframe, applies a payload only if its version is strictly newer than the installed one and only while no plugin call is in flight, caches it in clientStorage `grip.payload`, and rolls back (old handler, cache untouched) if evaluating it throws. **The handshake, pairing, WebSocket and update-strip logic live in the shell page, so a change to THAT, to the shell main thread, the verifier, the pinned keys or the manifest needs a manual re-publish in Figma; everything else ships as payload or as a signed `ui` patch script.** In a loader flavour `installedPluginVersion()`/`syncPluginCopies()` are off (no copy refresh, no reopen nudge) and a window reporting `shellProtocol >= 1` never blocks the update signal. Wire: `payload.json` = `{layout:1, header:{shellProtocol, flavour, version}, code, ui, sig}`, signed (Ed25519, release key) over `grip-payload|1|<shellProtocol>|<flavour>|<version>|<codeBytes>|<uiBytes>\n` + code + ui (`signingMessage` in `scripts/payload.mjs`, mirrored in `loader-ui.js`; `src/bridge/test/fixtures/payload-vector.json` pins them). After the pairing gate the shell sends `{type:'payload_have', flavour, shellProtocol, version}` and the bridge answers `{type:'payload', envelope}` (newer), `payload_current` or `payload_unavailable` (one answer per socket per 5 s); the shell reports `payload_report {status, version, code?}`. Replay rule: only a strictly newer version is applied; a rollback is a normal forward release. A new payload waits for zero calls in flight (at most 2 minutes). Shell-to-main messages: `payloadGet/payloadInstall/payloadDrop` and back `payloadCache/payloadPending/payloadResult`. A flavour with `payloadLoader` must have `lockOverrides:true`; the release key must not be small-order (checked in `loadFlavour`).
- **Insecure-Grip guard (flavours with a watchlist; the public flavour has `enforcement:'off'` and an empty `watchlist`, so none of this runs there).** `flavour.json` `watchlist` lists other Grip builds (ports, home folder, status file, login item, launch label, MCP name, entry name, `minSecureVersion` floor). `ForeignGuard` (`foreign-guard.ts`, started by the daemon) runs `detectForeign` (`foreign-detect.ts`: read-only; a WebSocket probe reads the welcome frame and hangs up, plus the status file, `install.json` and entry file) at start and every 60 s, and clears itself when the problem is gone. A foreign bridge below the floor (unknown or unparseable version counts as below) is `insecure`; a listener that is not a Grip bridge is `unknown_service` (warn only: health and installer text). ALERT ONLY, never a block: the strip stays connected and green, its tooltip says "Insecure Grip found: update or uninstall" (`foreign_alert` frame, replayed on hello), and while the alert lasts a `{foreign_alert, pulse:true}` frame plus a toast through `notify` go to each file about once a minute (`FOREIGN_PULSE_MS` 60s, env `GRIP_FOREIGN_PULSE_MS`; the strip breathes red three times, `#state.foreignpulse`, static red under `prefers-reduced-motion`; one pulse and toast per FILE, not per window; the first announcement also pulses), a paragraph in the session `instructions` and a notice on the first successful tool result of EVERY session (no 3-day throttle), `grip_health` / `grip_update check` field `foreignGrip {state, version, floor, evidence, action, slug}`, installer and `update` output; the installer exits non-zero for an agent (stdin not a terminal) until the user picks `--continue-with-foreign`. `remove-foreign [--yes]` (`foreign-cli.ts`) lists, then with `--yes` removes it: a PURE planner (`planForeignRemoval`, `foreign-paths.ts` for per-OS paths and the `homeSafeToDelete` / `mcpEntryIsForeign` predicates) and a thin executor (`runPlan` through the `ExecIo` adapter: command line verified with `isDaemonCommand` before any kill, exact allowlisted paths only, the home folder re-checked right before the delete, no link followed, locked files retried then reported "removable after restart", every command `execFile` with an argument array). Tests use fake IO and the neutral fixture; `npm --prefix src/bridge run test:cross` runs them on every OS in CI.
- **Idle shutdown.** Daemon exits 60s after **0 shims AND 0 plugins**. While any Figma plugin is connected it stays warm. On-demand cold-start note below.

## Releasing (CI owns it)

Never create a tag or release by hand. **Nothing generated is committed**: `bridge/*.mjs`, `bridge/THIRD-PARTY-NOTICES.txt`, `figma-plugin/code.js` and `src/bridge/dist/` are gitignored build output; the release bundles are built ONLY in CI from source and exist only as release assets. A push to `main` that touches `src/**`, `scripts/**`, `flavour/**`, `CHANGELOG.md`, `package.json` or the workflow runs `.github/workflows/release.yml`: it reads `BRIDGE_VERSION`, asks `scripts/release-gate.mjs` whether the version is `create` (no release yet), `recover` (release is a draft or lacks assets) or `skip` (complete), and refuses to publish a version with no `## <version>` section in `CHANGELOG.md` (that section becomes the release notes). It then runs `npm ci` for both halves, `npm run build` (tsc + esbuild + `scripts/third-party-notices.mjs`: license allowlist MIT/ISC/BSD-2/BSD-3/Apache-2.0/0BSD over the production dependency tree, writes `THIRD-PARTY-NOTICES.txt`), (for a `payloadLoader` flavour the plugin build also writes the shell into `figma-plugin/` and the full plugin source into `build/payload/code.js`, gitignored `/build/`; its lockfile joins the notices walk) then `node scripts/payload.mjs` (builds and signs `build/payload/payload.json` with `GRIP_RELEASE_SIGNING_KEY`, no-op for other flavours, unsigned in a dry run), `scripts/bundle-hygiene.mjs` (no developer paths or secret-looking values in the bundles), `npm audit --omit=dev --audit-level=high` (release / dry-run only), `npm test` (which builds first), `scripts/package-release.mjs` (assets + `SHA256SUMS.txt`; also fails if the four version places disagree or a bundle does not contain the version), `scripts/sign-release.mjs` (writes `SHA256SUMS.txt.sig`, the Ed25519 signature the bridge requires: reads the PKCS8 PEM private key from the repository secret `GRIP_RELEASE_SIGNING_KEY`, fails loudly when it is missing or invalid, and self-verifies against the public key(s) in `flavour/flavour.json` `releaseKeys` so a wrong secret fails the job; a real release with the secret missing FAILS, a manual dry run skips signing), and a zip-install smoke test (its home dir derived from the flavour's `homeDirName`); the `publish` job (the only one with `contents: write`) creates release `v<version>`. To release: bump the four lockstep versions (`BRIDGE_VERSION` in `src/bridge/src/types.ts`, `PLUGIN_VERSION` in `src/plugin/code.ts`, `src/bridge/package.json`, `src/plugin/package.json`), add the CHANGELOG section, push (no build or generated file to commit). The `recover` path for an already published release recomputes `SHA256SUMS.txt` over the final assets, so the publish job re-signs it (it also gets the secret, for that step only). A release lacking `SHA256SUMS.txt.sig` is incomplete (`release-gate.mjs` `REQUIRED_ASSETS`, 9 for the public flavour; `requiredAssets()` adds `grip-plugin-payload.json` for a loader flavour, which `sign-release.mjs` also requires to be signed and listed in the sums) and is `recover`ed. **Public plugin pin:** `scripts/public-plugin-pin.test.mjs` hashes the built `figma-plugin/{code.js,ui.html,manifest.json}` (code.js with the `PLUGIN_VERSION` literal normalised) so a change to the public output is deliberate. Re-record with `npm run build && node scripts/public-plugin-pin.test.mjs --record` when you edit the plugin sources or `templates/*`, and when merging a branch that edits `templates/ui.html`. Rotating the signing key: ship a bridge whose `releaseKeys` lists both keys, wait for installs to update, then switch the secret. `workflow_dispatch` is a dry run by default (artifact only). Separately, `.github/workflows/test.yml` builds and runs the tests on every push and pull request on ubuntu, macOS and Windows (the full `npm test` off Windows, the Windows-safe subset everywhere).

## Flavours

## On-demand cold-start tradeoff

A Figma plugin opened **before** any agent has called grip shows disconnected — the Figma sandbox can't launch a local process, so plugin-open alone can't start the daemon. The first agent call spawns the daemon; the plugin's exponential-backoff WS reconnect latches within ~2s. From the agent's side the first call "just works" (the shim spawns + waits). Inherent to on-demand given Figma's sandbox; the alternative is a launchd always-on daemon.

## Error handling contract

- Plugin API errors → catch and `figma.ui.postMessage({kind:'response', id, error: msg})`; never crash plugin.
- **WS disconnect / reconnect (`maybe_applied`).** When a plugin session drops (or a call times out because the iframe respawned under a new sessionId), `dropSession`/`onTimeout` sort its requests: a **read** that was already sent (`isRetrySafe`: the plugin's `READ_ONLY_METHODS`, mirrored in `bridge/src/methods.ts` and drift-checked by `test/flow-multi.mjs`, minus `trigger_undo`/`notify`/`open_external_url`) and **any** call still only queued (never sent) are re-sent **once** on the newest live session of the same file (`fileIdentity`) if one appears within `PLUGIN_WAIT_MS` (3s), else rejected with `plugin_disconnected` saying it is safe to retry. A **change** that was already sent is never re-sent: it fails with `maybe_applied` ("the change may already have been applied, re-read before retrying"). A mutating `request_timeout` says the same. The shim's dropped-socket errors (`proxy.ts`) say re-read first (`data.maybeApplied`) only for a tool that can change the document (`toolMayChangeDocument` in `methods.ts`: anything that is not `isRetrySafe`, so also `trigger_undo`/`notify`/`open_external_url` (a lost undo retried blindly undoes twice); merged tools judged by their resolved op, plus an allowlist of bridge-side tools such as `list_files`, `grip_load_tools`, `subscribe`); for anything else they say it is safe to retry. `onTimeout` reports `plugin_reconnected` only when a NEWER window (later first hello) of the same file exists, so a genuine wedge with two windows of one file is still a timeout.
- Validate params before any Plugin API call. Standard messages: `"Node not found: <id>"`, `"Property '<prop>' not supported on node type <type>"`.
- **`node_not_found` fast-fail.** `figma.getNodeByIdAsync` HANGS forever on a removed/invalid id (Figma quirk) instead of returning null. The shared `getNode(id)` helper (used by every node-targeting handler) races it against `GETNODE_TIMEOUT_MS` (8s) → throws a typed `node_not_found` naming the likely cause (removed) plus the recovery for the rare false-positive (a valid node on an unloaded heavy page — make its page current first). This is why `get_node`/`get_nodes`/etc. no longer eat the full budget on a stale id.
- Bridge never logs to stdout. Anything informational → `process.stderr.write`.
- **Flow control (per-plugin concurrency cap + fair queue).** The plugin is single-threaded, so a *flood* of concurrent commands (many agents, or one client that pipelines) saturates it and wedges the window. `PluginBridge.request` meters each plugin to `MAX_INFLIGHT_PER_PLUGIN` (env `GRIP_MAX_INFLIGHT`, default 8) sent-and-awaiting at once; excess is held in a per-plugin queue with **one FIFO per MCP session**, and `pump()` serves the sessions **round-robin** (one call per waiting agent per turn), so one agent's burst can't starve another agent's single call. Transparent to the agent (it just awaits). The 10s request timer starts when a call is SENT, not when it is queued; the wait is logged (`queuedMs=` on the `«` line) and a wait of 2s or more is reported in the tool result's `_meta['grip/queuedMs']` (via the `callContext` AsyncLocalStorage, no signature change). Backstops shed with a typed `plugin_overloaded` carrying `retryAfterMs` (queue depth x recent reply latency, 250ms..30s): a session with more than `MAX_QUEUE_PER_SESSION` queued (env `GRIP_MAX_QUEUE_PER_SESSION`, default 125), or a plugin queue deeper than `MAX_QUEUE_PER_PLUGIN` (env `GRIP_MAX_QUEUE`, default 500). `grip_health` exposes per-plugin `inflight`/`queued`/`queuedSessions` (both lanes) and `writeLane {serial, inflight, queued}`. **Write lane:** for a plugin advertising `serialMutations`, every call the plugin serializes (`serializedByPlugin` in `methods.ts`: not read-only, plus `commit_undo`/`trigger_undo`; `UNDO_CONTROL_METHODS` drift-checked by `test/serial-writes.mjs`) goes through a separate lane with at most ONE in flight (`writeInflight`/`writeQueues`, same per-session round-robin FIFOs), so a write's budget timer starts when the plugin can actually run it and writes never take read slots; reads keep the `MAX_INFLIGHT_PER_PLUGIN` slots. The write lane is per FILE, not per window: during reconnect overlap (two windows of one file identity), `writeHeldElsewhere` holds a window's writes while another window of the file still has one in flight (until it settles, times out or that window drops), and every write release pumps all windows of the file (`pumpFile`), so a file never has two writes in flight. A write queued longer than `MAX_WRITE_QUEUE_WAIT_MS` (env `GRIP_MAX_WRITE_WAIT_MS`, 60s, counted from when it first entered a write queue, `writeWaitSince`) is rejected with `plugin_working`, never sent. A write that times out on the bridge while an EARLIER write that already timed out is still running in the plugin (`lostWrites`: timed-out writes with no late reply yet, per window) waited behind it inside the plugin and will be skipped there (`plugin_queue_timeout`), so its `request_timeout` says it was probably never started (still: re-read before retrying) instead of the plain `maybe_applied`. Plugins without the capability keep the single shared lane. Every request frame carries `timeoutMs` (the call's budget). `pump()` runs `busyCheck` on each queued call before sending it, so on a wedged/busy plugin queued calls fail fast instead of each burning a timeout. This is the **volume** guard; the busy guard below is the **single-frozen-op** guard, complementary.
- **Busy guard (`plugin_working` / `plugin_busy`).** The plugin runs on Figma's single main thread; a synchronous `run_script` loop freezes it and the bridge cannot preempt it. `busyCheck` (`ws-server.ts`) runs before the flow-control gate and judges each outstanding call against **its own budget** (`budgetFor`: 10s default, the `SLOW_METHOD_TIMEOUT_MS` table, or a run_script `timeoutMs`): (1) a call that ran past its budget with no reply (kept in `overdue` until any reply from that plugin, a drop, or `OVERDUE_FORGET_MS` 30s) and that no in-budget slow call explains -> new calls fail instantly with `plugin_busy` (probably wedged; reload the tab if it persists); (2) an ordinary call outstanding past `BUSY_THRESHOLD_MS` (5s) **in the same lane** (on a `serialMutations` plugin a long write never turns reads away and vice versa), or one waiting behind a slow call -> the retryable `plugin_working` naming the method holding the thread, how long it has run, and `retryAfterMs` (never says reload); (3) a slow call (export, page load, `map_nodes`, run_script with `timeoutMs`...) still inside its own budget is normal work and other agents' calls go through. A call that times out behind an in-budget slow call also gets `plugin_working` instead of `request_timeout`. `retryAfterMs` is in the message text (`retryAfterMs=<n>`) and in `_meta['grip/retryAfterMs']`. Env `GRIP_REQUEST_TIMEOUT_MS` / `GRIP_BUSY_THRESHOLD_MS` exist for tests.
- **Event routing.** `subscribe`d events are delivered only to MCP sessions that route to the event's file (`bridge.sessionTargets`, which runs `route()` on a throwaway copy of the session so pins/binds are untouched): bound -> only its file; unbound with one file open -> that file; ambiguous -> nothing. The notification `data` keeps `{event, payload}` and adds `fileKey`, `fileName`, `pluginSessionId` and `causedBy` (`bridge.eventCause`: `'self'` when this session has an event-causing call in flight on that plugin or one settled in the last 1.5s, which covers the 500ms documentchange debounce; `'other'` when only other sessions do; `'unknown'` when nobody does, likely the user, or when both do). Best effort, not proof.
- **run_script forensics.** `mcp-server.ts` logs the **full** `code` arg of every `run_script` to `~/.grip-bridge.log` (bracketed `run_script[<sid>] code: … /code`), bypassing `summarizeArgs`' 40-char truncation, so a freeze can be diagnosed post-mortem. The tool description carries hard guardrails (chunk + `await`, no unbounded sync loops, prefer `findAllWithCriteria`/bounded reads, small payloads).
- **run_script inspect-and-teach (the transport pushes back).** A *synchronous* loop can't be preempted once running, so `handle()` `inspectScript(code)` runs BEFORE eval and rejects the freeze patterns — `while(true)`/`for(;;)` and page/document-wide `figma.currentPage|root.findAll(...)` — with `run_script_rejected: …` messages that name the problem AND the better tool (so the agent learns, not just fails). The safe path is made a one-liner: the run_script scope now injects gentle bulk helpers — `findNodes(query)` (typed, via findAllWithCriteria; refuses a bare page walk), `forEachNode(itemsOrQuery, fn, {chunk,budget})` / `mapNodes(...)` (chunk + yield so the thread never freezes), and `yieldNow()`. For uniform bulk edits there's the **`map_nodes`** tool (Grip owns the loop entirely — query + `set`/`delete`/`rename`/`swap`/`applyStyle`, no JS). Guard regexes are a nudge for the common literal, not a security boundary; `node.findAll` on a bounded subtree is allowed.
